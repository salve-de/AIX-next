## 結論

ROVANは「顧客の必須作業を増やさず、競争状況を調べ、自社が選ばれる根拠を整え、その対応と結果を知らせ続けるサービス」とする。任意で顧客が取りたい客・勝ちたい比較軸・重点競合を選べる。ユーザーは労働者ではなく方針を示す人、ROVANは調査・整理・実行可能範囲の更新・再測定を担う。

継続価値は、目的との一致、実際の仕事、仕事と結果の可視化、過去の方針を踏まえる蓄積、次回も必要な調査の五つで作る。操作そのもの、ページ量、文章生成量、毎日ログインを目的にしない。

研究はこの設計を支持するが、ROVANの解約率改善幅を実証したものではない。本書の件数・通知頻度・価格・原価上限は初期設計案であり、顧客データによる実証値ではない。

## 1. 固定する製品ルール

| 項目 | 採用仕様 |

| 初回 | 社名またはURL、連絡先、契約・決済に必要な手続き。公開運用を選ぶ場合は対象企業と公開範囲の権限確認を初回に集約する |
| 日常利用 | 操作ゼロでも基本サービスが継続する |
| 任意参加 | 取りたい顧客、競争方針、重点競合、無関係な提案の除外。長文の自由入力は初版の中核にしない |

| 運営者 | 定例面談・個別原稿制作・手動レポート・他社への掲載交渉を商品に含めない |
| 顧客サイト | 初版では接続・書き換え・WordPress操作・PR承認を要求しない |

| 根拠不足 | 当該主張だけ見送り。他の監視は続行。ユーザーや運営者の確認待ちを恒常的に積まない |

## 2. 初期対象と市場での位置

最初は、日本語の公開サイトに商品・契約・導入条件がある、Webで比較検討されるB2B SaaS・ITサービス・専門的な法人サービスを優先する。業種だけでなく、公式情報を取れること、競合比較が成立すること、継続的な集客判断に情報を使えることを適合条件にする。

小規模だから拒否するのではないが、情報がほとんどない・比較対象が特定できない企業を大量広告の中心にしない。初回自動スキャンで適合性を確認し、不十分なものを無理に成功表示しない。

Peecの改善案、Profoundの自動ワークフロー、ScrunchのAI向け配信は既に存在する。従って「改善案が出る」「AIが自動で働く」だけを独自性としない。ROVANは、顧客が設定・制作を担当しなくても、会社理解→観測→機会→ROVAN側対応→結果確認までが既定動作でつながる体験を差別化の仮説とする。[S4-S6]

大企業の多国展開、汎用ワークフロービルダー、代理店向け多数顧客管理、CMS連携は初版の完了条件にしない。

## 3. 最初の体験

1. URLから公式情報・企業同一性・比較市場を調べる。同名の別会社などを一意に確定できなければ、対象の公開処理は止める。
2. 実際のAI回答と出典を取り、いま選ばれている条件・競合の強み・自社の未活用情報を返す。最初から質問票を置かない。
3. 十分な根拠のある最優先機会を1件、代案は最大2件提示する。機会が見つからなければ無理に3件作らない。
4. 「この方向を優先」「別の方向」「今は任せる」を任意で選べる。無操作も「任せる」として基本処理を継続する。
5. 選択されたら方針を保存し、追加調査の重点を変える。すでに進行中の仕事を毎回ゼロから再実行しない。
6. 実行可能範囲を処理し、次の比較時点と現状を表示する。通知を読むことや承認することを、次回実行の必須条件にしない。

初回の価値は「自社の具体的な機会を知ったこと」。初回の成功条件を「設定項目を全部埋めたこと」にしない。

## 4. 任意で触れる範囲

| 操作 | 変わるもの | 変えないもの |
|---|---|---|
| 取りたい顧客を選ぶ | 追加調査、優先案件、報告の冒頭 | 固定測定群の過去データ |
| 比較軸を選ぶ | 根拠の探索と説明の重点 | 料金・サービス実態 |
| 競合を重点指定 | 追加調査の割当 | 市場全体の基本監視 |
| 「競合ではない」 | 該当関係の扱いと追加調査 | 原典の過去記録 |
| 「安売りしない」 | 対抗案の除外条件 | 事実の記述 |
| 「もう知っている」 | 通知の重複抑制 | 重要な新規変更の監視 |
| 任せる | 標準運用を継続 | サービスの実行可否 |

選択肢は自社の確認済み情報から作る。「顧客が選んだから事実である」と解釈しない。意図と事実を別のデータで保存する。

方針は変更可能とし、変更前後の版・適用時点を残す。毎週同じ質問を繰り返さない。自由文で人間の運営者へ相談が流れる導線を中核にしない。

## 5. 競合弱点・自社強みの分析

弱点を次の三種類に分ける。

- 確認された条件差：競合は年契約、自社は月契約など。同じ商品・対象顧客・時点で比較する。
- 公開情報の不足：調べた競合ページで条件を確認できない。実際に対応していないこととは区別する。
- 観測上の弱さ：特定の固定質問群で候補入りが少ない。市場全体の実力差とは区別する。

機会として扱うために、自社の対応可能性、顧客方針との一致、競合との同条件比較、ROVANができる処理を確認する。自社にも根拠がなければ「強化できる」案件にはしない。

優先順位は、証拠と適合性を必須ゲートにしたうえで、選んだ顧客層との近さ、観測された質問との関連、ROVAN内での実行可能性、直近の変化、費用を組み合わせる。初版では「高・中・低＋理由」で十分。校正していない勝率や収益予測に変換しない。

AIへの質問は、原典URL・取得時刻・対象商品・数値の条件を返す形式にする。今週の収集は保存済みの先週の結論に誘導せず実施し、比較工程で初めて先週データと結合する。検索で出ないことを「存在しない」にしない。

## 6. 自動実行の範囲

### 自動で完了させる

公開情報の再収集、競合発見、AI回答観測、前週比較、事実の整合確認、方針に沿う優先順位、根拠付き説明、報告、再測定を基本機能とする。

許可されたROVAN管理の会社情報ページは、公式情報の値・条件・期限・対象を保持して更新できる。文章の装飾や未確認の優位性ではなく、すでに存在する情報の整理を行う。公開前の検証に失敗した項目は非掲載にし、監視全体は止めない。

### 準備までに留める

顧客サイトの料金ページ案、外部メディア掲載案、サービスそのものの改善案。これらは任意の持ち出し資料であり、顧客の宿題を商品価値の中心にしない。誰も公開しなければ「準備済み」のまま。

### 初版では実行しない

顧客サイトの改修、価格改定、認証取得、保証の追加、口コミ投稿、競合への接触、外部メディアとの交渉、無制限な原稿修正。

ROVANページの公開・更新は、AIに引用される保証ではない。通常の検索・取得条件を満たしても、インデックスや表示は保証されない。自動処理した事実と、露出改善を分けて測る。[S7]

## 7. 画面は三つの主領域に整理する

| 主領域 | 最初に見せるもの | 詳細で見せるもの |
|---|---|---|
| 今の状況 | 選んだ方針、重要変化、最優先案件 | AI別の回答・根拠・比較範囲 |
| 進めている案件 | 発見、対応中、反映済み、再測定の状態 | 変更前後・source・見送り理由 |
| これまでの成果 | 完了案件、観測変化、継続して追う対象 | 月次報告、長期履歴、方針の変化 |

既存のresultとwatchを利用し、同じデータの別ダッシュボードを何枚も増やさない。「設定」は常時操作する画面ではなく、会社方針の任意修正として提供する。

### 案件カード（架空の説明例）

> 御社の方針：少人数で導入する企業を優先
>
> 発見：競合Aは最低契約12カ月。御社の公式サイトでは月単位の契約が確認できました。
>
> ROVANの対応：契約期間・解約条件・適用プランを整理し、ROVAN管理の会社情報ページへ反映しました。
>
> 反映状態：保存と公開取得の確認が完了。
>
> 次の確認：「契約期間が柔軟なサービス」の定点観測を継続。
>
> 任意操作：この方向を優先／別の方向にする

これは実装後の表示例であり、実際の企業の条件・反映済み実績ではない。UIは実データに基づいて各欄を埋める。

## 8. 仕事と結果を別の台帳で保存する

案件の状態は「発見→方針適合確認→根拠確認→準備→適用→再測定」にする。これに「変更不要」「証拠不足」「取得失敗」「適用不可」を加える。

`applied`はプランが生成された時点ではなく、書込み成功・版の確定・公開取得確認の後に設定する。`remeasured`は測定が済んだことを意味し、改善したこととは別。

結果は「改善方向／横ばい／悪化方向／比較不能」に分ける。前後比較は因果効果ではない。更新後も引用されない・推薦が変わらない事例を保存する。

月次報告は実際の月内イベントから集計する。直近一回の観測件数を4倍しない。重複実行・同じ主張の反復更新を重複カウントしない。変化ゼロ・実行ゼロを表示できる。

## 9. 測定と追加調査を分離する

固定測定は、同じ質問・AI提供元・モデル/設定・地域/言語・回数で追う。会社方針が変わっても過去の定点測定を消さない。モデルや質問群を変える場合は新しい比較系列を開始する。

追加調査は顧客の方針と新しい競合に合わせて変更できる。追加調査の結果を固定測定の推薦率へ混ぜない。

AIが明示した選定理由は保存するが、内部の真の評価ウェイトとは呼ばない。生成した購入前質問は市場需要の実測ではない。

実観測の失敗は失敗として保存する。推薦・言及・否定的な言及を区別し、推薦された企業の抽出をテストする。各AIの結果を実際に別集計する。

比較対象は成功した同条件の観測。分母と欠測を併記する。少数観測での動きは暫定とし、条件を合わせた再測定で確認する。売上・商談の増加に換算しない。

ROVAN管理ページから公式サイトへのクリックなど、自分で取得できる経路の指標は別に測る。自社テスト・ボット・重複アクセスを除外し、クリックを受注扱いしない。顧客CRM連携を初版の必須条件にはしない。

## 10. 継続通知と価値の蓄積

初回は自社固有の機会を示す。次の比較では前回案件の続き。月次は「目的／実施内容／観測結果／未確認事項／来月も追う対象」を一枚で返す。

週次は読み切れる短い要約を標準とし、詳細は任意。重要な変化がない週も、監視の実施状況と対象範囲を短く伝える。臨時通知は高重要度で根拠のあるイベントだけ。通知を無視しても処理は止まらない。

「競合が変化→調査した→何を更新した→結果はどうか」を一本につなぐ。API回数だけを成果にしない。[S2-S3]

蓄積する会社記憶は、優先顧客、避けたい競争、重点競合、却下した提案と理由、過去の対応と結果。回答だけではなく次回の方針と仕事配分に使う。

経営者向けの短い要約と、担当者向け根拠は同じデータから生成する。初版で別レポート製品を作らない。外部共有は既定非公開とし、必要な場合に明示操作で共有リンクを作る。

## 11. 通常運用を自動化する設計

既存の週次測定、永続DB、課金、メール、ジョブ処理を利用する。新しい基盤を増やすための基盤移行はしない。

初期配分案は、固定測定を週1回、重点競合は原則5社、各社の重要ページは上限5ページ、案件の同時重点数は3件、新規競合探索は週1回。これは上限・優先度の初期設定であり、必ずこの件数の成果を作る義務ではない。

固定測定が50問×3系統×3回なら最大450観測/回。52週換算では年間23,400、月平均1,950観測となる。ただし、実際の月次レポートと原価は実行記録から集計する。

同一公開URLの取得は規約と利用権限に従って短期キャッシュできる。顧客固有の方針・結果は混ぜない。変化のないページは不要な再生成を抑え、重要変化だけ深掘りする。

会社別・実行別の費用上限を設け、優先度の低い探索から抑制する。基本サービスで約束した観測の不足を隠さない。直接原価を月額の20%以内に抑えることを初期の設計目標とし、実測で修正する。

失敗の再試行回数、タイムアウト、重複実行防止、途中保存、請求イベントの重複受信を標準で扱う。単発失敗は自動回復し、複数社にまたがる障害・原価異常・公開情報の誤りなどだけ運営者へ集約通知する。[S8-S10]

通常運用は自動化できても、障害・権利者からの申出・重大な誤情報対応が永久にゼロになる保証はしない。例外だけを短く確認できる管理画面に集約する。

新しいテーブルを無闇に増やす必要はないが、次の概念を独立して追跡する。

| Observation | 質問ID/版、モデル、提供元、実行時刻、回答、引用、成功/失敗、費用 |
| Opportunity | 方針版、競合根拠、自社根拠、関連質問、重要度理由、可否 |
| Action | opportunityId、種別、対象、準備/適用状態、before/after版、実行ID、失敗理由 |
| Outcome | actionId、比較対象の観測ID、分子分母、変化、比較可否、限界 |

## 14. 必須テスト

| テスト | 期待する挙動 |
|---|---|
| 全プロバイダ未設定 | 成功観測ゼロ。架空の推薦率を表示しない |
| 1社分だけ取得失敗 | 他社の処理は継続。当該データは欠測 |
| 否定文で自社名が登場 | 推薦扱いしない |
| 同名別会社 | 誤対象の公開・更新をしない |
| 競合のサイト未取得 | 公開情報未確認。非対応とは書かない |
| 初回に競合条件を発見 | 「変更」ではなく「初めて確認」 |
| 「年」という一字だけ存在 | 「豊富な実績」と生成しない |
| 自社価格が未公開 | 価格を生成せず、価格公開要求で運用を止めない |
| 方針を何も選ばない | 初回から週次・月次まで完走 |
| 方針を変更 | 探索と優先順位のみ変わり、過去の比較指標は維持 |
| 方針を連打 | 最新方針へ集約。重複課金・無制限実行なし |
| 公開DB更新失敗 | 適用済みにならない |
| 同じFactを再取得 | 同じ変更を再び成果カウントしない |
| AIごとに逆方向の変化 | 各提供元の実測を個別表示 |
| 5回の週次実行がある月 | 実際の月内成功実行を集計し、4倍に丸めない |
| 変化なし/悪化 | 隠さず状態を表示。無根拠な「侵食なし」としない |
| プロバイダモデル変更 | 旧モデル系列と区別し、単純前週比を止める |
| 共有レポート | 閲覧権限が限定され、失効でき、管理トークンを含まない |
| Webhook重複 | 1回分として処理。二重実行なし |
| 顧客操作ゼロで4週経過 | 監視・更新可能な処理・報告が正常に回る |

## 15. 検証・採用判断

主要指標は有料開始後90日/180日の企業単位の継続率。分母は観測期間を満了した全対象企業。キャンセル予定、支払い失敗、無料移行、年契約拘束中を区別する。年契約の支払済期間中の在籍は、自由に再選択した継続とは混ぜない。

補助指標は、初回の有効機会取得率、根拠を含む報告到達率、案件の実適用数、比較可能な再測定率、任意方針の採用率、適合しない提案の再発率、顧客別原価、手動介入率。ログインやメール開封は成果の代替にしない。

最初は全体を十分に動く水準に整え、その後、同じ基本機能・価格・契約条件で「任意方針選択なし」と「任意方針選択あり」を比較する。将来、仕事可視化の形式は別実験で検証する。少数顧客を最初から多数群に分散しない。

企業単位で無作為割当し、同じ会社の利用者には同じ体験を出す。操作した人だけではなく、割当された全社で比べる。必要数は既存継続率と検出したい差から決める。[S11]

有料顧客が少ない段階の10〜20社は、操作負担・不整合・価値理解の問題を発見する試験母集団であり、解約低下を統計的に確定するための十分な数とはみなさない。自然発生の任意フィードバックと利用ログを自動集計し、毎月全社面談は行わない。

## 16. 集客と収益化

入口は「会社URLで、競合が選ばれる条件と自社の使える強みを診断」。無料結果には自社固有の価値を出す。有料価値は継続観測・変化対応・履歴・ROVAN側の公開情報保守であり、単なる一回の点数表ではない。

集客は業種別の公開解説・利用可能な実事例・非公開の無料診断・任意の社内共有を優先する。SEO会社や制作会社は紹介チャネルとして試せるが、紹介報酬や代理店機能で継続性の弱さを埋めない。

単一標準プランで有料継続と原価を確認するまで、多数プラン・個別見積り・顧客ごとの特注対応は避ける。月49,800円は価格仮説であって、現在のコードの販売準備完了を意味しない。

税や経費を含めない単純計算では、月49,800円×62社＝月3,087,600円、年間37,051,200円。年間365日で割ると日平均約101,510円の売上。利益ではない。

大企業向けSSO、多国・多ブランド、CRM、代理店ワークスペースなどは、継続と運営原価の証拠を見てから拡張する。

## 17. 最初のリリース条件

販売前にP0を満たし、そのうえで「任意方針→機会1件→自動でできる処理→実行の証拠→同条件再測定→報告」を一本、実データで通す。いきなり全業種・全競合・全公開チャネルを網羅しない。

人が何も操作しない経路と、1回だけ方針を選んだ経路の両方を完走させる。生成しただけの画面・型定義・チェック済みIssueは実装完了の証拠としない。

完了後に初期有料顧客へ広げ、90日以降の継続と運営原価を見る。新機能の追加は、実際に価値が途切れた箇所を補うものから優先する。
